# UAT 策略与四大防回归原则

> 本文档是 `uat-tester` skill 的核心参考。写任何**角色专项 / 权限 / 数据范围 / 状态机**相关用例前必读。

---

## 1. 分层策略（不重复造轮子）

```
┌─────────────────────────────────────────────┐
│  E2E UI（主路径，本体系重点）                  │
│  用户旅程 / 模块用例 / 角色专项 / 状态流转       │
├─────────────────────────────────────────────┤
│  API 幂等预置造数（globalSetup + 工厂）         │
│  租户/组织/部门/用户/资源/记录...         │
├─────────────────────────────────────────────┤
│  既有单元/集成测试（不重复，作守卫）            │
│  JUnit/Jest/Vitest 等                        │
└─────────────────────────────────────────────┘
```

- **E2E 断言用户可见结果**（URL、菜单、文案、数据行、按钮可见性、toast），不依赖内部实现。
- **API 层仅用于造数与预置状态**（幂等 `ensure*` 工厂），不做主路径断言。
- **不重复既有测试**：后端状态机、路由守卫已由单测覆盖的，E2E 只验证用户视角。

## 2. 测试数据策略（隔离与幂等）

- 全部场景数据通过 API 幂等预置：**存在即复用，不存在才创建**；新建一律**时间戳命名**保证唯一可重复跑。
- `workers=1` 串行执行，避免写操作并发冲突。
- `globalSetup` 幂等：预置测试租户 + 组织 + 部门 + 全部角色账号，写 storageState。
- spec 之间不共享可变数据；资源/记录等每条用例独立造数。
- 状态预置（如「待审核记录」）用工厂直接置位，而非走完整业务流（不涉及的环节用 API 预置替代）。

## 3. 外部依赖降级策略

| 依赖 | 降级行为 | E2E 策略 |
|---|---|---|
| 地图（Google/高德/百度） | 显示「地图加载失败」占位 | 断降级占位文案，不依赖真实渲染 |
| 视频/直播流 | 显示「演示模式/未配置」占位 | 断占位文案（mock 开关） |
| 推送（WebSocket/SSE） | 无推送时无角标 | 不测实时推送，只测状态流转结果 |
| 第三方支付/短信 | 不真实发送 | 不触发或断 mock |

真实服务冒烟另标 `@live`，`grepInvert` 默认排除。

## 4. 四大防回归原则

### 4.1 首屏零噪音（Zero-Noise Landing）

**定义**：任何角色登录后，其**可访问的落地页/首屏**在加载过程中不得出现业务噪音错误（403 无权限、400 参数错误、500 服务器错误等 toast/alert），且该页面的**公共基础数据**（部门树、下拉选项、筛选器等公共数据接口）必须对「能进入该页面的所有角色」可用。

**为什么**：落地页 403 toast 是用户最先感知的缺陷，但传统 E2E 只断言「菜单可见/表格/按钮」，**从不断言「页面加载过程中不应出现 ≥400/错误 toast」**，导致此类缺陷在自动化里数月不被发现。

**强制要求（新增/修改角色用例必带）**：

1. 每个角色专项至少含一条「落地页零噪音」用例，模板：
   - 注册网络响应监听，收集 ≥400 响应，断言落地页加载完成后为空；
   - 断言页面不出现错误 toast（无「无权限/Request failed/Internal Server Error」匹配）；
   - 对页面依赖的筛选器基础数据接口做接口层断言（角色 token 直调 = 200），锁定根因而非仅看 UI。
2. 跨模块公共数据接口的权限语义遵循「对能进入该页面的所有角色开放」：
   - 筛选器（dept-tree / options / filter-options）→ 走 OR 权限域（如 `resource:read ∪ dashboard:view`），**不得只挂单侧权限域**；
   - 新增此类接口时，须在追溯矩阵标注其权限域，并给受影响角色补一条零噪音用例。
3. 评审 checklist：任何「菜单隐藏」类权限变更，必须同步核对**该角色可见页面所依赖的全部接口**（含**页面内嵌组件**的依赖——详情抽屉、弹窗、视频预览等），而非只核对菜单本身。

### 4.2 深链接与抽屉覆盖（Deep-Link & Drawer）

**定义**：零噪音断言不能只覆盖「登录后首屏」，还必须覆盖**可访问页面里的第二层交互**——点进详情、打开抽屉/弹窗、播放视频、触发导出等。这类交互依赖的接口往往不在首屏请求里，缺陷只在点击后才暴露。

**为什么**：首屏零噪音覆盖不到「打开详情抽屉 → 拉关联数据/直播流」这一步。详情抽屉的接口常锁单侧权限域，而菜单本身可见——菜单与接口的权限域不一致是本类缺陷的根因。

**强制要求**：

1. 每个角色专项至少选 1~2 个**有数据支撑的深链接入口**（如资源详情、详情抽屉、审批弹窗），断言打开后依赖接口零 ≥400、无错误 toast；
2. 深链接依赖接口同样遵循「对能打开该入口的所有角色开放」的权限语义（OR 域）；
3. 若测试数据难以预置（如远程记录），至少做**接口层断言**锁定权限域：角色 token 直调该入口的关键接口 = 200；
4. 导出/批量操作也属深链接——断言触发后接口 = 200、产物生成、无错误 toast。

### 4.3 数据范围按角色隔离（Data Scope Isolation）

**定义**：列表/详情/导出的数据行必须按角色数据范围过滤。不同角色有不同的数据可见范围——这是用户最敏感的越权点。

**为什么**：接口 200 ≠ 数据正确。若只断 200，数据范围回归（店长能看到异区订单）在 E2E 里永远发现不了。

**强制要求**：

1. 预置两个不同范围的数据点（如本部门记录 A + 其他部门记录 B）；
2. 目标角色视角断言：本部门 A 可见、其他部门 B 不可见（列表/搜索/详情均验证）；
3. 导出场景断言：导出内容不含其他部门数据（行数或关键字段）；
4. 接口层断言：返回数据的 `deptId/ownerId` 在允许集合内；
5. 数据范围策略枚举见 `roles-data-scope.md`，常见四类：ALL（全量）/ ORG（本组织及下级）/ DEPT（本部门）/ SELF（本人）。

### 4.4 幂等造数与隔离（Idempotent Provisioning）

**定义**：全部场景数据通过 API 幂等预置，存在即复用、不存在才创建、新建时间戳命名、串行执行、spec 间不共享可变数据。

**为什么**：不幂等 → 重复跑就冲突失败；并发 → 写操作互相覆盖；共享可变数据 → 用例间耦合，一个挂全挂。

**强制要求**：

1. 造数工厂统一 `ensure*` 命名，先查后建，存在即返回已有 id；
2. 新建数据用 `Date.now()`/UUID 后缀保证唯一可重复跑；
3. 状态预置（如「待审核」）用工厂直接置位（PATCH status），而非走完整业务流；
4. `workers=1` 串行；
5. spec 之间不共享可变数据；只读的预置数据（租户/组织/部门/角色账号）由 globalSetup 一次性预置。

## 5. CI 集成要点

- 触发：push（含 main/feature）+ PR；可 `workflow_dispatch` 手动。
- 步骤：checkout → setup 运行时 → 自建纯净环境（docker-compose + 后端 + 前端）→ 健康检查 → 跑 E2E → `if: always()` 上传产物。
- 超时留足（E2E 全量常 30~60 分钟）；失败可重试 job 拉取 trace 定位。
- `workers=1`，CI `retries=1`，本地 `retries=0`。
- 失败产物（report/trace/video/screenshot）作 artifact 上传。

## 6. 评审 checklist（新增/修改用例必过）

- [ ] 用例有 `UAT-<组>-<n>` 编号，映射到验收项（追溯矩阵已更新）
- [ ] 角色专项含首屏零噪音断言（§4.1）
- [ ] 角色专项含至少 1 个深链接/抽屉覆盖（§4.2）
- [ ] 涉及列表的用例有数据范围断言（§4.3，至少两个范围数据点）
- [ ] 造数走 `ensure*` 幂等工厂，新建数据时间戳命名（§4.4）
- [ ] 选择器优先 testid，不用脆弱 CSS/text 定位操作元素（§3 主文件）
- [ ] 登录态走 storageState 复用，spec 不重复登录
- [ ] 外部依赖断降级文案，不依赖真实服务
- [ ] 403/权限断言双轨：UI 无按钮 + API 角色token直调 = 403

# UAT Tester（通用用户验收测试体系）

## 0. 这个 skill 解决什么

UAT（用户验收测试）最容易写成「点一遍能跑就算过」的零散脚本——但没有角色矩阵、没有追溯矩阵、没有数据范围断言、没有零噪音防线。结果是：权限回归、数据越权、落地页弹错 toast 这类**用户最先感知的缺陷**在 E2E 里数月不被发现。

本 skill 把 UAT 当成一个**体系**来做：

1. **先文档化**：角色矩阵、验收清单、用例追溯矩阵（用例 ↔ 验收项双向追溯）、四大防回归原则的落地清单。
2. **再自动化**：按矩阵生成 E2E 脚本，统一选择器策略、幂等造数工厂、storageState 复用、零噪音断言模板。
3. **可回归**：接 CI，防权限/菜单/数据范围/状态机回归。

**框架无关**：Playwright / WebdriverIO / CodeceptJS / Appium / Detox / XCUITest 按被测栈选型，skill 只规定**约定与模板**，不绑死某一框架。

## 1. 工作流（每次激活按此走）

### 阶段 A：探查（能自动做的先做）

激活后第一动作是**探查被测系统**，而非直接写用例。并行执行：

- **前端路由/菜单**：扫 `router`、`menus`、`routes` 配置，提取全部可访问页面与菜单树。
- **testid/选择器约定**：grep `data-testid|testId|test-id|accessibilityIdentifier|testID`，判断现有选择器策略。若项目无 testid 约定，**第一步是推动加 testid**（见 §3），而非用脆弱的 CSS/text 选择器。
- **后端接口与权限域**：扫 controller/路由文件的权限注解（`@PreAuthorize|hasAuthority|@RequireAuth|canActivate|guard`），梳理「接口 ↔ 权限点」映射。
- **账号体系**：找 seed/fixture 里的角色账号、登录接口、token 机制（JWT/session）、storageState 可行性。
- **外部依赖**：识别地图/视频/支付/推送等外部依赖，确认是否有 mock/降级开关。无降级开关的，UAT 一律断降级占位文案而非真实服务。

探查产出**一份系统摸底笔记**（贴在对话里给用户看），作为后续用例设计的依据。

### 阶段 B：关键决策问用户（别替用户拍板）

探查后，这些决策**必须问用户**，不要自作主张：

1. **角色矩阵**：系统有哪些角色？每角色可见菜单/不可见菜单？数据范围策略（全量/本组织/本店/本人）？写权限差异？
2. **验收项清单**：有无现成 PRD/验收清单/需求文档？优先级 P0/P1/P2 划分？若无，由你起草后让用户确认。
3. **用户旅程**：挑哪几条端到端剧本串联（如「管理员创建资源→编辑者更新内容→审核者审批发布」）？
4. **被测形态**：本期覆盖 Web 后台 / C 端 H5 / App 的哪几个？三端都做还是先做一个？
5. **自动化栈**：用户偏好哪个框架？若无偏好，按被测栈推荐（见 `references/templates-web.md` 选型表）。

**问的时候用结构化多选**（`ask_followup_question`），一次性问清，别挤牙膏。

### 阶段 C：文档化（先矩阵后脚本）

按 `references/matrix-template.md` 产出：

1. **角色矩阵**：角色 × 菜单可见性 × 数据范围 × 写权限。
2. **验收清单**：每条验收项编号（`<域>-<序号>`，如 `AUTH-01`），标优先级。
3. **用例追溯矩阵**：用例编号 `UAT-<组>-<n>` ↔ 验收项 ↔ 实现文件 ↔ 自动化状态（✅/🅿️P0本批/⏳二期）。
4. **四原则落地清单**：哪些角色专项要带零噪音断言、哪些深链接入口要覆盖、哪些数据范围要断言、哪些造数要幂等。

文档放 `docs/uat/` 或项目约定位置，让用户先审。

### 阶段 D：自动化（按矩阵落地脚本）

矩阵确认后，按 `references/templates-*.md` 生成脚本。核心约定见 §3。

### 阶段 E：回归与 CI

- `workers=1` 串行（写操作并发必冲突）。
- `globalSetup` 幂等预置角色 + storageState，spec 不重复登录。
- 失败产物（截图/trace/video）落 `test-results/`，CI 作 artifact 上传。
- 接 CI：push/PR 触发，纯净环境自建 → 健康检查 → 跑 E2E → 上传产物。

## 2. 四大防回归原则（内建，必落地）

这四条是从真实事故提炼的硬约束，不是可选项。详细背景与模板见 `references/strategy.md`。

### 2.1 首屏零噪音（Zero-Noise Landing）

任何角色登录后，其**可访问的落地页/首屏**加载过程中不得出现业务噪音错误（403 无权限、400 参数、500 服务器错误等 toast/alert），且该页依赖的**公共基础数据接口**（部门树、下拉选项、筛选器等公共数据接口）必须对「能进入该页的所有角色」可用。

落地方式：每个角色专项至少一条「落地页零噪音」用例——监听网络响应收集 ≥400，断言落地后为空；断言无错误 toast；对关键筛选器接口做接口层断言（角色 token 直调 = 200），锁定根因而非仅看 UI。

### 2.2 深链接与抽屉覆盖（Deep-Link & Drawer）

零噪音不能只覆盖首屏，还必须覆盖**可访问页面里的第二层交互**——点进详情、打开抽屉/弹窗、播放视频等。这类交互依赖的接口往往不在首屏请求里，缺陷只在点击后才暴露。

落地方式：每个角色专项至少选 1~2 个有数据支撑的深链接入口，断言打开后依赖接口零 ≥400、无错误 toast；若测试数据难预置，至少做**接口层断言**锁定权限域。

### 2.3 数据范围按角色隔离（Data Scope Isolation）

不同的角色有不同的数据可见范围（如管理员看全量、部门经理只看本部门、普通用户只看自己的数据）——这是用户最敏感的越权点。E2E 必须断言**列表/详情/导出的数据行**按角色数据范围过滤，而非仅断言接口 200。

落地方式：预置两个不同范围的数据点（如本部门记录 + 其他部门记录），目标角色视角断言本部门可见、其他部门不可见；导出场景断言行数/内容；接口层断言返回数据的归属字段（如 `deptId/ownerId`）在允许集合内。

### 2.4 幂等造数与隔离（Idempotent Provisioning）

全部场景数据通过 API 幂等预置：**存在即复用，不存在才创建**；新建数据一律**时间戳命名**保证唯一可重复跑。`workers=1` 串行。spec 之间不共享可变数据。状态预置（如「待审核」记录）用工厂直接置位，而非走完整业务流（不涉及的环节用 API 预置替代）。

## 3. 自动化核心约定（框架无关）

- **选择器优先 testid**：`data-testid`（Web）/ `testID`（RN）/ `accessibilityIdentifier`（iOS）/ `testId`（Android）。无 testid 的项目，第一步推动加 testid，而非用 CSS/text 选择器（脆弱且改文案即崩）。text 选择器仅用于断言文案，不用于定位操作元素。
- **POM 页面对象层**：选择器与操作封装在 Page Object，spec 只描述业务步骤。一页一 POM，操作返回 self 便于链式。
- **storageState 复用登录态**：角色登录由 globalSetup 一次性预置到 storageState，spec 直接复用；登录本身由专项 spec 覆盖，不重复登录。
- **降级断言不依赖真实外部服务**：地图/视频/支付/推送一律断降级占位文案，真实服务冒烟另标 `@live` 默认排除。
- **403/权限断言双轨**：UI 侧断言无操作按钮（如无保存按钮）；API 侧用角色 token 直调断言 = 403，锁定根因。
- **用例命名与标记**：`UAT-<组>-<序号>`，`@auth @dashboard @rbac @journey @crud @live` 等标记分组，`grepInvert @live` 默认排除真实服务用例。

- `scripts/gen-matrix.py` —— 交互式生成空追溯矩阵 Markdown（角色矩阵 + 验收清单 + 用例矩阵），避免手敲表格。

## 6. 不做什么

- 不重复既有单测/集成测试（后端状态机、路由守卫已覆盖的不重造）。
- 不测真实外部服务渲染（地图/视频/支付/推送——断降级文案，`@live` 另行）。
- 不把改库/改种子当 E2E 主路径（造数走 API 工厂，不直连 DB）。
- 不替用户拍板角色矩阵/验收范围/优先级（阶段 B 必须问）。
- 不用脆弱选择器（CSS class / 易变文案定位操作元素——改文案即崩，是 E2E 维护地狱的根因）。
